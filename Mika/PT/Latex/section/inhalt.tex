\section{Einleitung}
Diese Konzeption beschreibt die automatische Provisionierung einer vollständig serverlosen Todo-Anwendung
in der AWS Cloud~\cite{jain2021serverless, wen2023rise}. 
Die Lösung nutzt moderne Infrastructure-as-Code (IaC) Prinzipien mit Terraform als 
primärem Automatisierungstool \cite{ozdogan2023systematic, hashicorp2024terraform}  
und implementiert eine CI/CD-Pipeline für kontinuierliche Bereitstellung.

\textbf{Kernkomponenten:}

\begin{itemize}
    \item \textbf{Frontend:} Angular SPA gehostet auf Amazon S3 mit CloudFront CDN~\cite{cloudfront2012performance, tyagi2025optimizing}
    \item \textbf{Backend:} AWS Lambda Functions für CRUD-Operationen~\cite{hussain2024performance, tanneru2024serverless}
    \item \textbf{Datenbank:} Amazon DynamoDB für hochperformante NoSQL Datenspeicherung \cite{haseeb2017review, ahmed2018literature}
    \item \textbf{API Gateway:} RESTful API-Endpunkte mit integrierter Authentifizierung
    \item \textbf{Authentifizierung:} RESTful API-Endpunkte mit integrierter Authentifizierung 
\end{itemize}

\textbf{Automatisierung:} Infrastructure-as-Code mit Terraform, GitHub Actions CI/CD Pipeline, 
und automatisierte Tests.

\section{Infrastructure-as-Code (IaC) Strategie}

\subsection{Terraform als Provisionierungstool}
Bei der Auswahl eines geeigneten Infrastructure-as-Code (IaC) Tools stehen verschiedene Optionen zur Verfügung, 
die jeweils unterschiedliche Stärken und Schwächen aufweisen. Im Folgenden werden die wichtigsten Alternativen 
zu Terraform analysiert und deren charakteristische Eigenschaften gegenübergestellt.
Die Bewertung der verschiedenen Tools erfolgt anhand mehrerer kritischer Dimensionen, die für die 
erfolgreiche Implementierung von Infrastructure-as-Code-Projekten entscheidend sind.

\begin{table}[h!]
\centering
\begin{tabular}{>{\bfseries}p{3cm}p{2.5cm}p{2.8cm}p{2.2cm}p{2.5cm}}
\toprule
\textbf{Kriterium} & \textbf{Terraform} & \textbf{AWS CloudFormation} & \textbf{AWS CDK} & \textbf{Ansible} \\
\midrule
Multi-Cloud & \yes & \no & \no & \yes \\[0.3cm]
Lernkurve & \partialyes & \partialyes & \textcolor{darkred}{\warn~Schwer} & \textcolor{darkgreen}{\yes~Einfach} \\[0.3cm]
Community & \textcolor{darkgreen}{\yes~Sehr groß} & \partialyes & \textcolor{darkorange}{\warn~Klein} & \textcolor{darkgreen}{\yes~Groß} \\[0.3cm]
Syntax & \textcolor{darkgreen}{\yes~HCL} & \textcolor{darkorange}{\warn~JSON/YAML} & \textcolor{darkorange}{\warn~Code} & \textcolor{darkgreen}{\yes~YAML} \\[0.3cm]
State Management & \textcolor{darkgreen}{\yes~Explizit} & \textcolor{darkgreen}{\yes~Implizit} & \textcolor{darkgreen}{\yes~CloudFormation} & \textcolor{darkred}{\warn~Schwach} \\
\bottomrule
\end{tabular}
\caption{Vergleichsmatrix der Infrastructure-as-Code Tools}
\end{table}

\begin{itemize}
    \item \textbf{AWS CloudFormation} stellt als nativer AWS-Service eine solide Grundlage für 
    AWS-spezifische Infrastrukturen dar. Die enge Integration in das AWS-Ökosystem bietet Vorteile 
    bei der Verwaltung von AWS-Ressourcen, jedoch beschränkt sich die Anwendbarkeit ausschließlich 
    auf die Amazon-Cloud-Plattform. Die JSON- oder YAML-basierte Syntax kann bei komplexeren 
    Infrastrukturen schnell unübersichtlich werden.
    \item \textbf{Terraform} ist ein Open-Source-Tool, das eine deklarative Syntax in HashiCorp 
    Configuration Language (HCL) verwendet. Es bietet Multi-Cloud-Unterstützung und 
    eine große Community, die kontinuierlich zur Weiterentwicklung beiträgt. Die explizite 
    Verwaltung des Zustands ermöglicht eine präzise Kontrolle über die Infrastruktur, was 
    insbesondere bei komplexen Umgebungen von Vorteil ist.
    \item \textbf{AWS CDK (Cloud Development Kit)} ermöglicht die Definition von Infrastruktur 
    mittels vertrauter Programmiersprachen wie TypeScript, Python oder Java. Während dies für 
    Entwickler attraktiv erscheint, erhöht sich dadurch die Komplexität erheblich, da sowohl die 
    jeweilige Programmiersprache als auch die CDK-spezifischen Konzepte beherrscht werden müssen.
    \item \textbf{Ansible} zeichnet sich durch seine einfache YAML-Syntax und die niedrige 
    Einstiegshürde aus. Als primäres Konfigurationsmanagement-Tool konzipiert, weist es 
    jedoch Schwächen im Bereich des State Managements auf, was bei der Verwaltung komplexer 
    Infrastrukturen problematisch werden kann.
\end{itemize}

Die Entscheidung für Terraform als primäres Provisionierungstool basiert auf der Kombination aus
Multi-Cloud-Fähigkeit, starker Community-Unterstützung und der expliziten Verwaltung des Zustands.
Diese Eigenschaften ermöglichen eine flexible, skalierbare und wartungsfreundliche Infrastruktur,
die den Anforderungen moderner Cloud-Anwendungen gerecht wird.


\subsection{Terraform-Projektstruktur}
Die Projektstruktur für die Terraform-Konfiguration folgt den Best Practices
für eine modulare und wartbare Architektur. Die Hauptkonfigurationsdateien befinden sich im
Wurzelverzeichnis, während spezifische Module und Umgebungen in separaten Verzeichnissen organisiert
sind. Diese Struktur ermöglicht eine klare Trennung der Verantwortlichkeiten und erleichtert die
Wiederverwendbarkeit von Code.

\newpage
\begin{lstlisting}[style=terraform, caption=Terraform Projektstruktur]
terraform/
|-- main.tf                 # Hauptkonfiguration
|-- variables.tf            # Input-Variablen
|-- outputs.tf              # Output-Werte
|-- terraform.tfvars        # Umgebungsspezifische Werte
|-- backend.tf              # Remote State Configuration
|-- modules/
|   |-- api-gateway/        # API Gateway Module
|   |-- lambda/             # Lambda Functions Module
|   |-- dynamodb/           # DynamoDB Module
|   |-- s3-cloudfront/      # Frontend Hosting Module
|   `-- cognito/            # Authentication Module
`-- environments/
    |-- dev/
    |-- staging/
    `-- production/
\end{lstlisting}

\subsection{Beispiel Terraform-Code}

Die Hauptkonfiguration für die Todo-Anwendung umfasst die Definition der AWS-Provider,
die Konfiguration der Ressourcen und die Integration der Module. Die folgenden Code-Snippets
zeigen die wichtigsten Teile der Terraform-Konfiguration, einschließlich der Definition von
Variablen, Modulen und Ressourcen.

\begin{lstlisting}[style=terraform, caption=Hauptkonfiguration (main.tf)]
# main.tf
terraform {
  required_version = ">= 1.5"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = var.aws_region
  
  default_tags {
    tags = {
      Project     = "TodoApp"
      Environment = var.environment
      ManagedBy   = "Terraform"
    }
  }
}

# DynamoDB Table
module "dynamodb" {
  source = "./modules/dynamodb"
  
  table_name   = "${var.project_name}-todos-${var.environment}"
  environment  = var.environment
}

# Lambda Functions
module "lambda_functions" {
  source = "./modules/lambda"
  
  environment     = var.environment
  dynamodb_table  = module.dynamodb.table_name
  dynamodb_arn    = module.dynamodb.table_arn
}

# API Gateway
module "api_gateway" {
  source = "./modules/api-gateway"
  
  environment    = var.environment
  lambda_functions = module.lambda_functions.function_arns
  cognito_user_pool_arn = module.cognito.user_pool_arn
}
\end{lstlisting}

\begin{enumerate}

    \item \textbf{Monitoring:} Health Checks und Alerting
\end{enumerate}

\subsection{GitHub Actions Workflow}

\begin{lstlisting}[style=yaml, caption=GitHub Actions Deployment Workflow]
# .github/workflows/deploy.yml
name: Deploy Todo App Infrastructure

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

env:
  AWS_REGION: eu-central-1
  TF_VERSION: 1.5.7

jobs:
  terraform:
    name: Terraform Plan/Apply
    runs-on: ubuntu-latest
    
    steps:
    - name: Checkout code
      uses: actions/checkout@v4
      
    - name: Setup Terraform
      uses: hashicorp/setup-terraform@v2
      with:
        terraform_version: ${{ env.TF_VERSION }}
        
    - name: Configure AWS credentials
      uses: aws-actions/configure-aws-credentials@v2
      with:
        role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
        aws-region: ${{ env.AWS_REGION }}
        
    - name: Terraform Init
      run: terraform init
      working-directory: ./terraform
      
    - name: Terraform Plan
      run: terraform plan -no-color
      working-directory: ./terraform
      
    - name: Terraform Apply
      if: github.ref == 'refs/heads/main'
      run: terraform apply -auto-approve
      working-directory: ./terraform
\end{lstlisting}

\subsection{AWS-Authentifizierung für Terraform}

\subsubsection{IAM Roles mit OIDC (Empfohlen)}

\begin{lstlisting}[style=yaml, caption=AWS Credential Configuration]
- name: Configure AWS credentials
  uses: aws-actions/configure-aws-credentials@v2
  with:
    role-to-assume: arn:aws:iam::123456789012:role/GitHubActionsRole
    role-session-name: GitHubActions-TodoApp
    aws-region: eu-central-1
\end{lstlisting}

\textbf{Vorteile:}
\begin{itemize}
    \item Keine langlebigen AWS Access Keys
    \item Automatische Token-Rotation
    \item Granulare Berechtigungen pro Repository
\end{itemize}

\subsection{Anwendungssicherheit}

\subsubsection{Lambda Function Security}
\begin{itemize}
    \item VPC-Integration für Netzwerk-Isolation
    \item Environment Variables für Konfiguration
    \item AWS X-Ray für Tracing und Monitoring
    \item Least Privilege IAM Roles
\end{itemize}

\subsubsection{API Gateway Security}
\begin{itemize}
    \item Cognito Authorizer für alle Endpunkte
    \item Request/Response Validation
    \item Rate Limiting (1000 requests/minute)
    \item CORS-Konfiguration
\end{itemize}

\subsubsection{DynamoDB Security}
\begin{itemize}
    \item Encryption at Rest aktiviert
    \item Encryption in Transit (TLS)
    \item Point-in-Time Recovery
    \item VPC Endpoints für private Zugriffe
\end{itemize}

\section{Fazit}
Abschließend lässt sich festhalten, dass die serverlose Todo-Anwendung auf AWS eine moderne, skalierbare und wartungsarme Lösung darstellt. Die Verwendung von Infrastructure-as-Code mit Terraform ermöglicht eine effiziente Verwaltung der Infrastruktur und eine nahtlose Integration in CI/CD-Pipelines
Folgende Best Practices wurden implementiert, um eine robuste und sichere Anwendung zu gewährleisten:
\begin{enumerate}
    \item \textbf{Infrastructure as Code:} Alle Änderungen über Git versioniert
    \item \textbf{Immutable Infrastructure:} Keine manuellen Änderungen in AWS Console
    \item \textbf{Security by Design:} Least Privilege Principle durchgehend angewendet
    \item \textbf{Cost Awareness:} Regelmäßige Cost Reviews und Budget Alerts
    \item \textbf{Disaster Recovery:} Automatisierte Backups und Rollback-Prozesse
\end{enumerate}
