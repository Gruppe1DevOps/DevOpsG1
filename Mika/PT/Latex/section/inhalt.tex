\section{Einleitung}
Dieses Dokument beschreibt die Planung, wie eine To-Do-App in der AWS-Cloud automatisch bereitgestellt 
werden kann. Das Ziel ist es alle nötigen Komponenten automatisch über Infrastructure-as-Code 
(IaC) bereitzustellen. Die Lösung besteht aus Benutzerschnittstelle, Backend, Datenbank und 
Sicherheitskomponenten.

\section{Technologieauswahl}
\subsection{Terraform als Provisionierungstool}
Als primäres Provisionierungstool wurde Terraform gewählt, da es Plattformunabhängigkeit ermöglicht 
und eine Multi-Cloud Strategie unterstützt~\cite{terraform-docs-overview}. Die deklarative Syntax in Form 
von HashiCorp Configuration Language (HCL) sorgt für gut lesbare und wartbare 
Konfigurationen~\cite{terraform-hcl}. Das integrierte State-Management erlaubt die Nachverfolgung
aller Ressourcen~\cite{terraform-state-docs}. 
Dank der großen Community und der umfangreichen AWS-Modulbibliothek~\cite{terraform-registry} 
lassen sich konsistente Architekturen über verschiedene Umgebungen hinweg realisieren. Als Alternativen 
wurden AWS CloudFormation~\cite{cloudformation-docs} und Pulumi~\cite{pulumi-docs} evaluiert, jedoch 
aufgrund von Vendor-Lock-in bzw. anderer Architekturansätze verworfen.


\subsection{Architekturübersicht}
Die Architektur der To-Do-Applikation (vgl. Abbildung~\ref{fig:architektur}) basiert
auf einer Serverless-Architektur in der AWS-Cloud. Das statische Frontend wird in einem 
S3-Bucket gehostet und weltweit über CloudFront als Content Delivery Network (CDN) 
ausgeliefert. API-Anfragen gelangen von CloudFront zum API Gateway, das als Schnittstelle 
zwischen Frontend und Backend dient~\cite{aws-serverless-whitepaper}. Die Backend-Logik ist in 
Lambda-Funktionen implementiert, welche die Geschäftslogik abbilden und mit DynamoDB 
für die Speicherung der To-Do-Items interagieren~\cite{aws-lambda}. Die 
Benutzerauthentifizierung und -verwaltung erfolgt zentral über AWS Cognito.

Die Kommunikation zwischen den Komponenten folgt einem klar definierten Fluss, hierbei dient CloudFront als 
zentraler Einstiegspunkt und leitet statische Inhalte an den S3-Bucket sowie API-Aufrufe an das 
API Gateway weiter. Das API Gateway wiederum leitet die Anfragen an die entsprechenden Lambda-Funktionen 
weiter, die für die Geschäftslogik zuständig sind. Die Lambda-Funktionen interagieren mit DynamoDB 
für CRUD-Operationen und mit Cognito für die Authentifizierung. Der S3-Bucket kommuniziert direkt 
mit Cognito für den Login-Prozess.

\section{Umsetzungskonzept}
\subsection{Authentifizierung in AWS}
Die Authentifizierung in AWS erfolgt auf mehreren Ebenen, um die größt mögliche Sicherheit zu gewährleisten.
Für die CI/CD-Pipeline werden spezielle IAM-Rollen für Jenkins, oder GitLab-Runner konfiguriert,
die temporäre STS-Tokens für Ephemeral Environments erhalten. Die lokale 
Entwicklung erfolgt über die AWS CLI, mit benutzerbasierten Zugriffsschlüsseln. Für 
Produktiv-Accounts ist Multi-Faktor-Authentifizierung (MFA) obligatorisch. 
Sensible Daten werden zentral im AWS Secrets Manager verwaltet~\cite{aws-secrets-manager}. 
Die Sicherheit wird durch das Least-Privilege-Prinzip in den IAM-Policies~\cite{aws-least-privilege} 
sowie durch automatische Schlüsselrotation~\cite{aws-key-rotation} gewährleistet.

\subsection{Provisionierungs-Workflow}
Der Provisionierungs-Workflow ist vollständig automatisiert und beginnt mit einem Code-Commit 
im Git-Repository, wodurch eine Pipeline in Jenkins oder GitLab CI ausgelöst 
wird~\cite{jenkins-docs,gitlab-ci-docs}. Die Terraform-Konfigurationen werden initialisiert,
ein Plan erstellt und automatisierte Tests, insbesondere Security-Checks mit Checkov, 
durchgeführt~\cite{terraform-docs-overview, checkov-docs}. Für die Produktivumgebung ist eine manuelle 
Freigabe erforderlich, nach dieser wird der Terraform-Apply-Prozess ausgeführt. Der 
Infrastrukturzustand wird in einem S3-Bucket mit Locking-Mechanismus gespeichert, um parallele 
Änderungen zu verhindern~\cite{terraform-state-s3}.

\section{Vor-/Herausforderungens}
\subsection{Vorteile}
Die gewählte Architektur bietet zahlreiche Vorteile, durch die Verwendung von Infrastructure-as-Code werden 
identische Umgebungen gewährleistet, was die Konsistenz über verschiedene Deployment-Stages hinweg 
sicherstellt~\cite{aws-iac-bestpractices-alt}. Die vollständige Provisionierung kann in 
weniger als zehn Minuten abgeschlossen werden, was die Geschwindigkeit der Entwicklung und des Deployments erheblich 
steigert~\cite{terraform-docs-overview}. Die Kostentransparenz wird durch konsequentes Tagging aller Ressourcen 
gewährleistet~\cite{aws-resource-tagging}. Die Sicherheit profitiert von der versionierten Konfiguration, 
die Compliance-Anforderungen erfüllt~\cite{opa-terraform}.

\subsection{Herausforderungen}
Trotz der vielen Vorteile gibt es auch Herausforderungen zu bewältigen, die Terraform-Syntax und die AWS-Services 
erfordern eine gewisse Einarbeitungszeit. Das Zustandsmanagement erfordert ein sorgfältiges Handling der state-Dateien,
um Konflikte zu vermeiden~\cite{terraform-state-best-practices}.
Die Fehlersuche bei Abhängigkeitsproblemen kann komplex sein und erfordert ein tiefes Verständnis der
Infrastruktur-Komponenten.

\section{Technische Umsetzung}
\subsection{Terraform-Modulstruktur}
Die Terraform-Konfiguration ist in logische Module aufgeteilt, die jeweils spezifische Aspekte der 
Infrastruktur verwalten, diese Module umfassen Netzwerk, Datenbank, Backend, Frontend und Sicherheit. 
Diese Struktur ermöglicht eine klare Trennung der Zuständigkeiten und erleichtert die Wartung und 
Erweiterung der Infrastruktur~\cite{terraform-module-best-practices}.

\subsection{Beispiel: DynamoDB-Provisionierung}
Ein konkretes Beispiel für die Provisionierung ist die DynamoDB-Tabelle für die To-Do-Items. 
Die Tabelle wird mit Pay-per-Request-Billing konfiguriert, was eine kosteneffiziente 
Skalierung ermöglicht. Die ID wird als Hash-Key definiert, und die Tabelle wird mit 
entsprechenden Tags für die Umgebung und das Management versehen.

Die automatisierte Provisionierung mit Terraform ermöglicht reproduzierbare, sichere und 
kosteneffiziente AWS-Umgebungen für die To-Do-Applikation. Durch modularen Code und 
CI/CD-Integration wird der Entwicklungslebenszyklus optimiert.
